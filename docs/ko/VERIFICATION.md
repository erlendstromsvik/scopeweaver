[네이티브 HTTP 우선순위 회귀 검사](../../server/ollama_priority_test.go)는 워커 1을 `/api/chat` 안에서 대기시키고 워커 2·3을 줄 세운 뒤, 호출자 쪽 우선순위 표시 없이 실제로 연결된 승인 판정기를 실행합니다. `-race`에서 실제 HTTP 순서 **워커 1 → 승인 판정기 → 워커 2 → 워커 3**, 최대 동시 실행 1, 유효한 네이티브 스키마·판정, 모든 호출 완료와 대기 슬롯 반환을 확인했습니다. 기존 대기열 검사는 역할별 FIFO·취소·상한 축소를 확인합니다.

[네이티브 원본 프로필 실패 회귀 검사](../../server/provider_origin_failure_test.go)는 수정 전에 실패했습니다. 네이티브 도구 호출이 대기 중인 상태에서 스트림 오류가 나면 전역 클라우드의 `allow` 기본값을 적용할 수 있었습니다. 수정 후에는 Stream·Complete·최종 라우팅 오류에서도 실제 네이티브 프로필, 모델 판정의 90초·`ask`, 사람 승인 대기의 300초·`deny`를 유지하며 판정 모델을 호출하지 않습니다. 실제 클라우드 전환 시에는 네이티브 선호를 지웁니다. 회귀 검사와 관련 race 검사는 통과했습니다.

실제 인증 API를 통해 요청을 외부로 전달하지 않는 로컬 프록시에서 엄격 모드를 **false → true → false**로 바꿨습니다. 검색 백엔드 4개(`ddgs`, `brave-free`, `tavily`, `deepseek`) 모두 엄격 모드가 꺼졌을 때만 프록시에 도달했고, 켜졌을 때 추가 요청은 각각 0개였습니다. 엄격 모드에서 업데이트 확인·적용은 차단하면서 로컬 상태는 제공했습니다. [업데이트 회귀 검사](../../server/update_policy_test.go)는 캐시·리디렉션·실시간 본문 읽기와, 이미 시작한 비동기 다운로드가 정책 전환으로 막힐 때 임시 파일 정리·실패 완료도 확인했습니다. 이 결과는 호스트 전체의 외부 통신 차단을 입증하지 않습니다.

호스트 Ollama **0.32.15**와 기존 `qwen3:4b`를 **출력 한도 4,096토큰**으로 사용해 네이티브 진단, decision/comment 스키마, 구조화된 도구 호출·결과 재전달, 사용량과 요청한 32K 문맥(`/api/ps`: **32,768**)을 확인했습니다. 이전 256·512토큰 한도에서의 실패도 증거로 유지하며 성공으로 처리하지 않았습니다. 로드·속도·오프로딩 관측값은 모델이 올라간 상태의 한 번 실행 결과로, 성능 측정이나 상주 보장이 아닙니다. 모델 다운로드·호스트 설정 변경은 없었으며, 자율 작업 완료나 보안 평가 품질을 주장하지 않습니다.

브라우저 검사는 세 언어의 진단·경고, 엄격 모드 업데이트 상태, 승인 설정의 로드·실패 보호와 기존 대시보드·사용량 흐름을 포함합니다. 시각 QA에서 최소 너비가 420px인 편집기가 390px 화면의 왼쪽으로 30px 벗어나는 문제를 재현했습니다. 최소 너비가 화면에 맞도록 수정한 뒤 다시 빌드한 앱에서 60개 검사를 모두 통과했습니다. 데스크톱·모바일 캡처 6개에서 글자가 잘리지 않고 내용이 화면 안에 있는지 확인했으며, 독립적으로 다시 빌드한 내장 바이너리는 브라우저 검사에 사용한 파일과 바이트 단위로 일치했습니다. 정확한 최종 커밋의 원격 CI와 PR 확인은 별도 전달 단계입니다. 병합·릴리스·유료 제공자 호출·외부 대상 스캔·실제 알림 전송을 주장하지 않습니다.

이 검사는 해당 통신 형식과 자격 증명 경계를 입증하며, 유료 계정의 사용 가능 여부나 과거 모든 기능을 입증하지는 않습니다. 수정 후 전체 테스트, 브라우저, CI, 병합된 main, 릴리스 산출물 검사는 별도 단계입니다. 유료 제공자를 실제로 호출하지 않았습니다.

| 독립 백엔드 보안/정확성 검토 | 통과. DeepSeek 로컬 전용 정책, 실시간 CIDR 점검, 404 분류 포함 |

### 실제 Ollama 실행

호스트의 Ollama 0.32.15와 `qwen3:4b`를 기본 스트리밍 API로 사용했습니다.

- 합성 도구 픽스처를 쓴 SDK 수준 스트리밍 점검에서 모델이 `record_fact` 도구 호출을 만들었고, ScopeWeaver가 이를 로컬에서 실행해 결과를 다시 전달한 뒤 턴이 완료됐습니다. 플랫폼 데이터베이스의 `record_fact`는 아닙니다.
- 32K 문맥을 요청했고 `/api/ps`는 32,768이 할당됐다고 보고했습니다.
- 이 점검의 정확한 사용량: 스트리밍 턴은 입력 186 / 출력 750 토큰, 완료 턴은 입력 826 / 출력 193 토큰입니다.
- 실제 API로 키 없는 저장·활성화가 통과했습니다. 진단 결과는 `tool_call_verified`와 `context_verified` true, 문맥 32,768, 로드 2.225375ms, 초당 29.231 토큰, 지연 18,958ms입니다. **모델이 이미 올라간 상태에서 한 번 실행한 결과이며, 콜드 스타트 성능 측정이나 하드웨어 일반화가 아닙니다.**
- 누락 모델에 대한 정확한 한국어 pull 안내와, 엄격 정책 전환 시 공인 IP 차단이 통과했습니다.
- **플랫폼 작업 워커 Bash 증거:** `qwen3:4b`(32K 요청, 32,768 할당, 동시 실행 상한 1, keep-alive 30m, thinking 끔, 최대 4,096 토큰)로 실행한 실제 작업 워커(작업 1)가 기본 Bash 도구 호출 `call_219yv72x`를 만들었습니다. 활동 9(호출)와 10(`tool_result`)이 같은 ID를 가지며 오류가 없고, 출력에 표시 문자열 `LOCAL_TASK_OLLAMA_OK`가 있었습니다. 이 기본 호출의 사용량 기록은 정확히 입력 6,704 / 출력 4,096 토큰이며, 다음 기본 호출이 같은 `tool_call_id`를 다시 전달했습니다. 의도(intent)는 기존 `db.AddIntent`로 직접 넣은 것이며 LLM이 만든 것이 아닙니다. 출력에는 픽스처 이스케이프로 인한 문자 그대로의 `\n`도 있으며, 이를 근거로 줄바꿈 처리나 모델 버그를 판단하지 않습니다. 이 실행은 최종 UI/DTO 변경 전, 커밋되지 않은 브랜치 소스로 빌드한 바이너리를 사용했습니다.

### 자율 작업 신뢰성은 검증되지 않음

도구 호출 진단 통과는 전송 경로가 동작함을 보여 줄 뿐, 모델이 작업을 끝낼 수 있음을 보여 주지 않습니다.

- `qwen2.5-coder:7b`는 `tools`를 선언하지만 실제 `tool_calls` 대신 `assistant.content`에 도구 호출처럼 보이는 JSON을 썼기 때문에 Bash나 사실 기록 도구가 실행되지 않았습니다. ScopeWeaver는 이를 올바르게 텍스트로 유지했습니다.
- `qwen3:4b`는 주 에이전트로 긴 프롬프트를 받았을 때 고민만 이어 가다가 기대한 표시 문자열을 텍스트로 썼습니다. 작업 워커로서는 위와 같이 Bash를 실행했지만, 작업은 `record_fact`나 자율 완료 없이 360초에 일시 중지됐습니다. 워커 도구 호출이 한 번 성공했다고 자율 완료가 입증되지는 않습니다.

**어떤 로컬 모델에 대해서도 처음부터 끝까지의 자율 작업 완료나 보안 평가 품질을 주장하지 않으며, 7B급 모델은 완전한 에이전트로 검증되지 않았습니다.** [하드웨어 등급](llm-providers.md#하드웨어-등급)은 성능 측정값이 아니라 추정치입니다.

### 실행하지 않은 범위

유료 클라우드 호출, 외부 대상 스캔, 실제 알림, 게시, 배포, 릴리스, 병합은 하지 않았습니다. Anthropic, OpenAI Chat/Responses, 사용자 지정 게이트웨이는 전송 계약 테스트, 회귀 점검, 수정 가능한 브라우저 흐름으로 확인했으며 실제 제공자 계정은 사용하지 않았습니다. 모든 테스트 데이터베이스는 일회용이었고 호스트 Ollama 설정은 바꾸지 않았습니다. 선택형 `local_llm_only` 정책은 기본값이 꺼져 있으며, 서버에는 `OLLAMA_NO_CLOUD`를 별도로 설정해야 합니다.

### 당시 기존 문제

`TestGraphOverviewExpandsAssociatedCompanyScope`는 ScopeWeaver와 수정하지 않은 원본 모두에서 `task scope missing: <nil>`로 실패했습니다. 이 테스트는 그래프 개요에 상세 범위가 포함된다고 기대했지만, 원본 커밋 `06a43f3`에서 개요를 의도적으로 간결하게 바꿨습니다. 커밋 `75a706d`에서 `TestGraphOverviewKeepsAssociatedCompanyScopeCompact`로 교체해 간결한 개요를 확인하고 저장된 회사 범위를 직접 검증합니다. 이후 전체 백엔드 CI는 통과하고 있습니다.

원본 검증에서는 `TestTaskMetadataPatchReturnsRenameAndPin`의 임시 디렉터리 정리가 간헐적으로 실패했습니다. 최종 ScopeWeaver 서버 검사에서는 통과했으며, 이를 숨기기 위한 별도 수명 주기 변경은 하지 않았습니다.

원본 데모에는 알림 메타데이터 모의 응답이 없어 데모 알림 페이지에서 오류가 납니다. **실제 백엔드의 알림 페이지와 채널 추가 폼은 두 언어 모두 통과**했습니다. 검증 중 알림은 전송하지 않았습니다.

v0.1.0 검증에서는 **npm 감사 결과 14건(심각 1, 높음 9, 보통 4)**이 기록되었습니다. 프레임워크·개발 도구 업데이트와 사용하지 않는 shadcn CLI 의존성 제거 후 위의 v0.2.1 후보에서는 모두 해소되었습니다. 현재 레지스트리 결과는 `cd web && npm audit`로 확인하세요. 새 보안 권고가 공개되면 감사 결과는 달라질 수 있습니다.

- 사용자 입력, 저장된 증거, 수정한 프롬프트, 통신 식별자, 기존 파싱 표시, 유니코드 테스트 데이터, 업스트림 원본 화면은 보존합니다. 임의의 사용자 데이터와 외부 도구 출력은 자동 번역하지 않습니다.
- `sidequestion/`의 과거 검증 문서는 새 ScopeWeaver 실행이 아닌 업스트림 기록입니다.

현재 원격 검사 결과는 [GitHub Actions](https://github.com/cskwork/scopeweaver/actions/workflows/ci.yml)에서 확인할 수 있습니다.
